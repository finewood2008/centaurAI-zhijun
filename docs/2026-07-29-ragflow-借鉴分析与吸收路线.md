# RAGFlow 借鉴分析与吸收路线

> 日期：2026-07-29
> 对标对象：[infiniflow/ragflow](https://github.com/infiniflow/ragflow)（Apache-2.0，86k+ star）
> 本方产品：centaurAI-database
> 部署目标：x86 (AMD) 盒子，单机单用户，本地优先

## 一、结论

RAGFlow 对我们的价值是**架构设计参考，不是依赖**。

功能维度上我们已基本对等，音视频多模态明显领先；真实差距集中在两处：**PDF 版面/页码溯源**和**ingestion 编排与任务持久化**。架构维度差别很大，但属于"量级差别"而非"路线差别"——它是为多租户云服务设计的，我们是单机单用户，直接引入会带来不成比例的运维成本。

不建议引入 RAGFlow 本体，建议选择性吸收其设计。

## 二、双方架构画像

### RAGFlow

一个重要信号：**正在从 Python 迁往 Go**。仓库语言统计 Go 16.1MB 已超过 Python 12.3MB，`internal/` 是全新 Go 分层，`rag/`、`agent/`、`deepdoc/` 为遗留 Python，两套并存，入口 `cmd/ragflow_server.go`。这是为规模化与运维成本做的重构。

- 分层：`handler` → `service` → `dao` → `engine`，各层独立可测，Go 侧几乎每文件配 `_test.go`
- 检索引擎抽象：`internal/engine/` 支持 elasticsearch / infinity / clickhouse 可换
- 存储抽象：`internal/storage/storage_factory.go` 支持 minio / s3 / gcs / oss / memory
- ingestion：`internal/ingestion/` 下 `pipeline` + `component` + `registry` + `task`，组件注册式可编排
- 中间件依赖（docker-compose-base.yml）：ES/OpenSearch/Infinity、MySQL/OceanBase/SeekDB、Redis(valkey)、MinIO、NATS、ClickHouse、Jaeger、TEI(CPU/GPU 双镜像)
- 交付：多套 compose + helm chart

### centaurAI-database

- 单进程 FastAPI，端口 8618，零中间件依赖
- 持久化：嵌入式 ChromaDB（`hnsw:space=cosine`）+ SQLite + JSON 文件 + 本地文件系统
- 模型：全本地。`bge-small-zh-v1.5`（24MB）+ Chinese-CLIP ViT-B/16 图文同空间；`embedder.py:43-56` 的 `_get_device()` 已有 `torch.cuda.is_available()` 分支；本地 ollama HTTP 接入，按需加载/卸载
- 检索：稠密向量 ∪ BM25（jieba + rank_bm25）→ `bge-reranker-base` 交叉编码器精排，人工重要度加权 + 置顶必回（`annotations.py`）
- 已有 MCP（stdio + Streamable HTTP 2025-11-25 + OAuth）与 memory（SOUL/AGENTS/IDENTITY/USER + journal 向量化 + Context Pack）
- 分层现状：`server.py` **3024 行 / 103 个路由**，router 直接操作 store，无 service/repository 分层
- ingestion：`watcher.py` `ThreadPoolExecutor(max_workers=1)` 单 worker + watchdog 目录监控，任务状态在内存

### 对比表

| 维度 | centaurAI-database | RAGFlow | 判断 |
|---|---|---|---|
| 中间件 | 零 | 十余个容器 | 我们是优势，不是缺陷 |
| 分层 | 单文件 3024 行 / 103 路由 | 四层 + 全量测试 | 真实差距 |
| 检索引擎 | 直绑 ChromaDB | 三引擎可换抽象 | 差距，但暂无驱动 |
| 存储 | 本地文件系统 | 五后端工厂 | 不需要 |
| 混合检索 | 稠密 ∪ BM25 → rerank | 多路召回 + 融合重排 | 基本对等 |
| MCP | 已有，含 OAuth | 2025-08 支持 | 不落后 |
| memory | 已有，含 Context Pack | 2025-12 支持 | 我们更贴场景 |
| 音视频 | 抽帧+CLIP+OCR+whisper，秒级时间戳 | 需外挂 | **我们领先** |
| PDF 版面 | pymupdf 纯文本流 | DeepDoc/MinerU/Docling | **真实差距** |
| chunk 溯源 | 音视频有 start_time，PDF 无页码 | 页码 + 可视化干预 | **真实差距** |
| ingestion 编排 | 单 worker 硬编码串行 | 组件注册式 pipeline | 真实差距 |
| 任务状态 | 内存，重启丢失 | 持久化 + NATS/Redis | 真实差距 |
| 模型接入 | 本地 ollama + 按需卸载 | 独立 TEI 容器 | 单机场景我们更优 |

## 三、x86 迁移带来的变化

部署目标从 RISC-V 改为 x86 后，此前以"riscv64 无构建路径"为由排除的选项重新可选：主流容器镜像、ES/pgvector/Infinity、GPU 加速、MinerU/Docling 等重解析器。

约束回归到**单机资源预算与运维复杂度**，不再是指令集。

随之而来，几处按小盒子设定的保守配置可能在白留性能：

| 位置 | 当前值 | 说明 |
|---|---|---|
| `config.py:91` | `RERANK_MAX_CANDIDATES = 12` | 偏紧，直接影响召回质量 |
| `config.py:97` | `RERANK_MAX_PASSAGE_CHARS = 256` | 偏紧，长句被截断 |
| `config.py:149` | `MAX_FRAMES_PER_VIDEO = 40` | 封顶 CLIP 嵌入量 |
| `config.py:219` | `WIKI_AI_KEEP_ALIVE = 0` | 用完即卸载模型，反复加载有开销 |
| `config.py:221` | `WIKI_AI_MIN_AVAILABLE_MEMORY_MB = 2600` | 内存门槛按小盒子设 |
| `embedder.py:332` | `device="cpu"` | faster-whisper 硬编码 CPU，未走 `_get_device()` |

## 四、吸收路线

### 第一梯队：立刻做，收益确定

**1. 带位置的解析产物 + PDF 页码溯源**

现状：`parser.py:69-78` 的 `_parse_pdf` 逐页 `page.get_text()` 后 `"\n\n".join(texts)`，**页号在这一行被彻底丢弃**。下游 `chunk_text(text, size, overlap)`（`parser.py:235`）只收字符串、返回 `list[str]`，没有位置信息通道。

关键有利条件：写入层**不需要改**。`add_file_chunks` 已有 `per_chunk_metadata` 参数（`vector_store.py:139`），视频转写块正是靠它携带 `start_time`/`modality`。PDF 页码复用同一条通道即可。且 `_NUMERIC_KEYS`（`vector_store.py:130`）已支持数值型 metadata 的范围过滤。

改造要点：
- `_parse_pdf` 返回 `list[(page_no, text)]` 而非拼接字符串
- `chunk_text` 接受分段输入，输出每块对应的页范围
- 跨页 chunk 记 `page_start` / `page_end`，单页 chunk 记 `page_no`
- 将 `page_no` 加入 `_NUMERIC_KEYS` 以支持按页过滤
- 检索侧在返回结构中补页码字段（参考 `vector_store.py:315-318` 对 `start_time` 的处理）

RAGFlow 将此单独建模为 `internal/ingestion/pipeline/pdf_pages.go`（配套测试），印证其为独立关注点而非解析器副产品。

**2. 放开保守配置**

在 x86 盒子上重新标定第三节表格中的各项，`faster-whisper` 改走 `_get_device()`。先压测再定值，不要凭猜调整。

**3. ingestion 任务状态落盘**

`watcher.py:53` 单 worker + 内存态，重启丢队列。仓库已有 23 处 sqlite3 使用，将 `submit_index` / `get_job` 状态迁至 SQLite 属小改动，可独立完成。不要引入 NATS/Redis 任务总线。

### 第二梯队：x86 新解锁，值得评估

**4. PDF 版面解析器（MinerU / Docling）**

此前因 RISC-V 构建不通而排除，现门槛消失。可获得表格结构与多栏版面信息，是第 1 项的上位替代，但代价是重型依赖 + 显著变慢。

建议顺序：先完成第 1 项（pymupdf 保留页号，改动小、立即可用），运行一段时间后观察 PDF 质量问题是否集中在表格与多栏版面；若是，再将 MinerU 作为**可选解析后端**引入，而非默认替换。

**5. ingestion 组件化编排**

参考 `internal/ingestion/pipeline/` 的 `pipeline.go` + `builtin_registry.go` + `component_params.go`，将解析→切片→embedding→索引拆为可注册组件。x86 上多 worker 并行不再有资源顾虑，可与第 3 项合并推进。改造面较大，排在第一梯队之后。

### 第三梯队：等驱动

**6. 检索引擎窄接口**

`vector_store.py`（23KB）直绑 ChromaDB。x86 让 ES/pgvector 成为真选项，但 Chroma 在单机单用户场景够用。收一个 upsert/query/delete 窄接口的成本不高，但建议等明确驱动（如需要真正的 filtered vector search，或数据量级上升）再做。

**7. 拆 `server.py`**

3024 行 / 103 路由的单文件是当前最大工程债。功能域其实已切清（`wiki_store` / `memory_store` / `annotations` / `vector_store` / `gbrain_store`），仅路由挤在一处。按域拆为 router 模块（mobile / search / context / wiki / memory / config / pairing），**只搬不改逻辑**，风险低。

此项与 RAGFlow 无关，但 database 已成主推产品，这笔债的利息将持续累积。不必照抄其四层结构，增加一层 router/service 分离即可。

## 五、明确不吸收

| 项 | 理由 |
|---|---|
| ES/OpenSearch/Infinity、MySQL/OceanBase、NATS、ClickHouse、Jaeger | 服务多租户云规模；我们零中间件是优势 |
| 多存储后端（minio/s3/gcs/oss） | 与本地优先定位冲突，本地文件系统足够 |
| 独立 TEI 推理容器 | 本地 ollama + 按需卸载在单机场景更优 |
| Go 重写 | 其动机是多租户运维成本，我们不适用 |
| helm chart / 多套 compose | 单机部署不需要编排层 |

x86 让这些**技术上**可行了，但它们服务的规模与我们不同，运维复杂度的代价没有变化。

## 六、下一步

建议从第一梯队第 1 项动手。需要先通读 `parser.py` 全文与 `vector_store.py` 的 metadata 写入路径，产出 PDF 页码溯源的完整改造方案，含跨页 chunk 处理规则与检索侧返回字段定义。
