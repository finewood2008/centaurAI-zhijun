依赖与边界：桌面仍通过主进程 → Consumer SDK → Agent → DE 的受控 HTTP 通道。当前每项业务读取采用 start/poll 两步，不擅改签名路由或响应合同。磁盘全库扫描成本另有证据，尚未纳入本次最小补丁。

验证须覆盖：ready 缓存期限、未完成/错误不缓存、并行请求合并、过期响应不跨连接回填、引导更新失效；poll 通知竞态、并行读取、取消/吊销、SSE 首块；PNG 外缘真实 alpha 与实际 Dock 显示。记录合成基准和真机观测的不同范围，不宣称未测的端到端耗时。

新增主 agent 任务：首屏五项读取需要十次 start/poll 请求，另有初始 context 与控制请求。短时 token 桶由 8 调为 12，使正常首屏不因本地补充 token 等待 600 ms 阶梯；native 同时执行上限仍为 8，业务上限 7，滚动 60 秒总量 100 / 业务 92、会话 1000、上传预留与未知写入策略不变。验收增加五项读取与心跳组合，并复验滚动窗口、会话和上传配额。

### 对话任务风暴与发送参数修复（0907 最终追加）

现场的“读取请求过多”来自任务槽耗尽，而不是 HTTP 协议没有生效。桌面业务仍经 Direct HTTP 的 start/poll 通道访问盒子；当时同一工作区已有 1024 个持久任务，其中大量读取由三个常驻刷新源制造：附件状态、画像授权状态及路由设置。现已分别改为仅在过渡态轮询、完成或空列表后停止、失败指数退避，并移除路由设置每 10 秒无条件读取。页面进入、打开设置、消息完成和用户显式操作仍会主动刷新。最新桌面构建在对话页空闲观察 15 秒期间，盒端路由任务计数保持 `93 → 93`。

盒端容量补丁在满额创建新任务前，只回收完成超过一小时且明确标记 `mutating=false` 的读取任务，按最旧顺序降到 75% 低水位。真实工作区首次从 `1024` 降至 `770`；8 个当时已有的写任务全部保留。后续现场操作增加了写任务，补丁仍只回收读取，不能把写入墓碑或未知标记当作可删除对象。

“请求参数不符合要求”的根因位于桌面传输适配层：路由预览和正式消息按业务合同共用 domain `body.requestId`，旧代码又把它作为 Gateway job `requestId`，第二个不同 operation 因幂等冲突在主进程内被拒绝，正式 `/messages` 没有到达盒子。现在每个 Gateway 传输任务生成独立随机 ID；业务正文中的 domain ID 保持不变，用于预览与正式消息关联。声明了 `Idempotency-Key` 的确认类操作仍按 catalog 使用稳定传输 ID。

真机使用公司盒 `AMD-A2A-248` 复测：同一业务 ID 的预览与正式消息均成功，问题“你是哪个模型”收到盒端模型完整回复，界面没有再出现参数错误或 429。加入原材料局部刷新回归后，前端全量 **80/80**、Shell 全量 **143/143**、Electron E2E **4/4**、产品导航 E2E 与 Desktop 构建通过。

账号登录态另设固定 7 天本地截止时间，凭据只保存在系统加密存储；普通关闭应用会保留，显式退出会先清除本地凭据。重启真机应用两次均自动恢复账号并进入设备选择页。`SESSION_EXPIRED` 和已经确认关闭的 `CONNECTIVITY_SESSION_EXPIRED` 都会清除账号、设备列表和加密登录记录，由现有桌面入口立即显示完整登录页。普通 Direct 建连失败、请求超时和权限拒绝仍保留账号，允许重新选择盒子。Access Token、Connectivity ticket、P2P session、逐请求证明和 workspace lease 继续使用各自短周期。

### “我的本体”按视图加载（0907 追加）

默认摘要原先同时发起 stats、当前分区 claims 和摘要全量 claims 三个业务任务，实际模板只消费摘要全量 claims。每项至少经过一次 start 和一次 poll，因此默认页面最低产生 6 次 SDK HTTP；导航提示缓存未命中时最低 8 次。

现按当前视图加载：摘要只取摘要 claims，全景才补 stats，列表/inbox 才取分区 claims 与 stats；成功返回空数组也记为已加载，视图来回切换不重复请求。默认业务任务由 3 降为 1，最低 SDK HTTP 由 6 降为 2。真实应用两次重启、生产登录并连接公司 `AMD-A2A-248` 后，顶部显示名称，自动化从“今日来信”进入“我的本体”分别约 658 ms、763 ms 出现摘要内容；观测包含 UI 自动化开销，不定义 SLA。详细调用边界见[接口去向审计](DESKTOP-API-ROUTING-AUDIT-0907.md)。

### 上传稳定性与原材料局部刷新（0907 追加）

公司盒日志确认 17:10 的 1,898,414 字节 PDF 上传经过 4 个分片、complete、业务导入和临时上传清理全部成功，后续资料列表、详情、摘要和分析任务继续成功。17:26 又通过真实桌面上传 101 字节验收文件，连接和心跳保持正常。两次上传前后整机 boot ID 不变，Agent、转发服务、Docker 与 Data Engine 重启计数均为 0，容器未 OOM。

17:11 的连接关闭发生在 PDF 业务导入成功约 15 秒之后。Agent 从 16:41:19 建立路径到 17:11:19 关闭相隔 1799.127 秒，与 Direct/P2P 票据的 1800 秒固定期限吻合；它是连接自然到期，并非上传导致盒子重启。当前产品按既定交互把 `CONNECTIVITY_SESSION_EXPIRED` 显示为重新登录。账号的 7 天本地期限不会延长 P2P 票据；若后续要求连续工作超过 30 分钟，需要设计安全的提前换票和会话切换，不能把短期票据直接延长到 7 天。

原材料列表原来在每次 1.8 秒轮询时设置全局 `loading`，模板会把整张表替换成加载提示；`setInterval` 还可能让慢请求重叠。现在首次进入才显示阻塞加载，已有数据时在后台刷新并保留稳定 `materialId` 行；自动轮询在上一次请求结束后才安排下一次。上传接口返回的真实资料行会先接替临时上传行，再执行列表核对，因此状态变化只更新对应行，后台失败也保留当前表格并提供局部重试。

### 原材料首屏与对话 409（0907 现场追加）

公司盒现场测量确认，盒内 loopback 业务接口不是主要瓶颈：`/api/mindos/folders` 为 1.4–3.2 ms，`/api/mindos/materials` 为 28–31 ms。桌面端每个逻辑读取需要一次 Gateway start 和至少一次 poll，并经 Electron、Consumer SDK、WebRTC Direct、Agent 和盒内 Gateway；Mac 到盒子的同期 ICMP 平均约 60 ms。原页面又先等待目录完成再请求资料，17:59 的两个真实任务分别为 310 ms 和 271 ms，创建时间相差 552 ms，从第一个创建到第二个完成约 823 ms。

现已将目录树和资料列表首屏请求并发发出。资料列表完成即可结束主内容加载，不再等待目录树；目录失败独立显示局部重试，也不会覆盖资料列表的成功状态。目录返回前，表格沿用资料接口给出的文件夹名称，避免短暂显示“未分类”。底层 native 1.2.1 支持并发请求，四次 start/poll 位于首批 12 个调度 token 内，不会触发 600 ms 补充阶梯。

Gateway 现网约有 802 个 jobs、2444 个 events 和 3249 个文件。事件写入原先分别为事件文件和 job 文件各递归扫描一次整个 workspace 配额；本轮在同一跨进程锁内复用一次配额快照，并按第一份文件的实际 allocation 更新后校验第二份文件。AES-GCM、payload reserve、文件与目录 fsync、写入顺序和跨进程配额锁保持不变。单次 `append_event` 的全目录 `_usage` 扫描由 2 次降为 1 次；创建任务的过期清理扫描仍保留。

18:08 的对话 409 来自路由预览内部的 `REDACTION_NOT_READY`。工作区有 3 份隐私资料，其中 1 份安全正文 ready、2 份处于 review_required；旧的自动 evidence 检索因任意一份安全正文未就绪而中断整次普通提问。服务端现在只在自动候选检索中跳过精确的 `REDACTION_NOT_READY`；显式选择资料、来源校验以及其他隐私错误仍严格拒绝，也不会回退读取原始正文。桌面同时把这两个隐私处理中错误码转换为可理解的提示，不再只显示“请求失败（409）”。
