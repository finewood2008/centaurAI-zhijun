# 知君单端、多端请求压力优化（2026-09-15）

## 范围与验收

第一阶段修改知君前端和 Electron 通信适配层。后续现场定位到历史任务容量耗尽，用户确认后增加第二阶段 Data Engine 网关容量修复（见文末）。不修改 Admin 登录限流、Remote Agent 配额，不自动重放对话、上传或其他写入。

验收标准：

- 对话后台整理期间不再同时运行两套 status 轮询；相同在途读取合并。
- 同会话反复收到任务事件不重启并叠加观察循环；停止、切页和总时限有效。
- 慢任务连续空结果轮询退避，有结果页继续立即读取，不重复创建业务任务。
- 客户端排队、盒端运行容量、盒端存储配额错误分别显示；只透传固定白名单错误码。
- 前端回归、桌面宿主回归、类型检查和桌面构建通过。

## 已确认的请求放大链路

已有对话首次打开会分批读取会话详情、授权、附件、事情、本体和整理状态等多个接口。业务请求在 Electron 中转换为一次 `POST /operations` 加一次或多次 `GET /operations/{id}`。

旧串行 native 通道不能被长轮询独占，因此 `business-bridge.cjs` 将调用方的 8 秒等待压到最多 250 毫秒。此前 renderer 收到空结果只等 25 毫秒，再发取结果请求。它不是重复模型调用，但会占用当前连接的请求预算。

对话页此前又同时有每 3 秒的 memory/routing/status 读取和独立的每 8 秒 status 读取；任务完成时还有重复刷新。

## 修改位置

| 层 | 文件 | 行为 |
| --- | --- | --- |
| 对话观察 | `frontend/mindos-web/src/composables/useMemoryAttentionPolling.ts` | 单会话合并观察、退避、总时限和终止状态 |
| 读取合并 | `frontend/mindos-web/src/composables/inFlightReads.ts` | 只共享正在执行的读取，不缓存旧结果，不重试写入 |
| 对话页 | `frontend/mindos-web/src/pages/ConversationPage.vue` | 统一 status 读取所有权、收敛结束刷新、隐藏辅助内容延迟加载 |
| 取结果节奏 | `frontend/mindos-web/src/desktop/pollPacing.ts`、`productClient.ts` | 连续空页逐级退避，间隔最多 2 秒，扣除本次请求耗时；有事件重置，等待可取消 |
| 错误边界 | `frontend/shell/runtime/product-policy.cjs`、`public-error.cjs`、`v2-request-scheduler.cjs` | 明确错误来源，保留受限诊断，不放宽配额 |

空结果退避意味着长时间无输出后，下一次检查可能最多多等约 2 秒；正在输出的连续事件页不增加这段等待。保留 250 毫秒 native 等待上限，避免恢复旧串行通道的阻塞问题。

## 错误分类

| 公开错误码 | 来源 | 自动重试 |
| --- | --- | --- |
| `CLIENT_BUSY` | 本机请求队列满或排队超时，尚未发出 | 否 |
| `BOX_BUSY` | 工作区 operation/session/worker/background/preview 容量，以及 `WORKSPACE_RESULT_CAPACITY` 暂时没有可用结果槽 | 否 |
| `WORKSPACE_STORAGE_FULL` | `WORKSPACE_OBJECT_LIMIT` 或 `WORKSPACE_QUOTA_EXCEEDED` | 否，需检查回收与存储 |
| `REMOTE_RATE_LIMITED` | 其他盒端 HTTP 429，未取得白名单原因 | 否 |

HTTP 429 本身不被当作“写入必定未执行”的证据。既有 SDK 重试仍仅限明确未派发的请求，最多两次。不会提高每连接的并发数、每分钟请求量或总请求额度。

## 发布与现场验收

第一阶段客户端修改需要重新构建并安装知君；第二阶段容量修复需要更新 Data Engine 盒端网关。代码修复不等于已经更新安装包或盒子。

现场分别验证单客户端和同账号双客户端：打开已有对话、发送一次消息等待整理、快速切页、停止生成；确认流式可见且没有重复消息。若仍收到 `WORKSPACE_STORAGE_FULL`，应检查实际磁盘和文件数配额；不能通过删除写入回执或取消配额绕过。

## 第二阶段：1024 历史任务容量修复

2026-09-15 对公司盒子只读核查：工作区有 1024 条任务记录，均已终止；其中 678 条写入记录（含 439 条已过期幂等回执）、346 条尚不满足旧一小时压力回收条件的读取记录。旧实现把这些记录统一计入 1024 个槽，即使没有正在执行的任务，也会拒绝新操作。此时运行中的桌面安装包仍为 0.1.22。

修复分工与边界：

- Data Engine `zhijun_gateway/store.py`：1024 限制改为完整任务结果容量；已过期终态回执不占结果槽，但继续受总磁盘和文件数硬限制。
- 容量满时，明确只读且终止已满 120 秒的结果可回收；写入或未知类型终止满 600 秒后只能压缩结果，不能删除幂等回执。时间从最后终态更新时间计算，运行和排队任务不作为候选。
- 回执保留稳定任务路径、请求指纹和所有权。先持久化回执，再删除事件；重启继续清理残留事件。同客户端旧写入 requestId 不会重新执行，内容不一致仍报幂等冲突。旧版本可识别回执，回滚可能重新触发旧容量限制，但不会因为换目录丢失防重信息。
- 常规结果 TTL 仍为 24 小时；容量压力下可能提前失效。读取过期结果返回 `JOB_RESULT_EXPIRED`，不能据此自动重发写入。
- Data Engine `manager.py`：保留工作区最多 12 个排队加运行任务、4 个同时执行；请求编号的容量豁免必须同时匹配客户端，取消和清理失败不能永久占用执行名额。
- 知君将新 `WORKSPACE_RESULT_CAPACITY` 映射为 `BOX_BUSY`，与总存储不足及真正限流区分，HTTP 429 不授权自动重试。

现场验收还需在部署后完成：保留既有任务及用户数据，打开今日来信、本体和对话，检查新增操作成功；测试同账号双端访问、主动取消和恢复旧写入，不出现重复执行。

## 注册验证码提示修复

Admin 的 `SMS_CODE_INVALID` 表示验证码错误或过期。知君此前仅在重置密码场景识别它，注册场景却归入 `INVALID_REQUEST`。现将注册场景也映射为 `VERIFICATION_CODE_INVALID`，提示“验证码错误或已过期，请重新获取后重试。”并保留关联编号。

仅按明确机器错误码映射，不将所有 HTTP 400/422 或服务端文字当成验证码错误；其它参数错误保留原分类。不改 Admin，不自动重试注册，也不展示手机号、密码、验证码或远端原始错误文本。此修改需要重新打包并安装知君生效。
