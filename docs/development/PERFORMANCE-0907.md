# 桌面刷新耗时修复（2026-09-07）

## 现象与定位

公司盒 `192.168.0.7` 已通过真实 Consumer/SDK v2 接入，用户仍看到对话列表长时间“正在加载”。桌面基线 `507edb5`，盒端 DE 为 `9fdff00`、worker 为知君 `507edb5`、Agent 为 `644b1c2`。

盒端代表性耗时：健康读取约 1–2 ms，v2 start 约 110 ms、poll 约 45 ms。桌面端实际进入对话页的一个完整样本约 6.24 秒，包含原生可访问性采样开销。

两个已确认的原因：

1. 原调度器强制每个原生请求间隔 600 ms。对话页面的多项读取分别需要 start/poll；三项并发读取在零服务耗时下仍累加约 3 秒本地等待。
2. SDK 1.2.0 sidecar 串行读取命令并等候完整 HTTP 响应。一个最长 8 秒的 poll 可能阻挡后面的普通读取、取消和心跳；TypeScript 层并发 Promise 无法消除这个等待。

## 当前调度合同

生产 bridge 先校验调用方原始请求，再仅将合法 operation poll 的 `waitMs` 截断至 250 ms；ID、after 游标及 `waitMs=0` 保留。Gateway 协议仍允许最大 8000 ms，当前桌面主动选用更短等待，适配已交付的串行 native。renderer、预览和流读取都经过同一 bridge。

调度器使用容量 8 的令牌桶，平均每 600 ms 补充一个令牌；业务保留一个令牌及一个原生在途名额给控制请求。所有派发尝试（含失败、重试、握手、心跳）纳入滚动 60 秒最多 100 次的硬限制；普通业务最多使用其中 92 个位置，剩余用于心跳和取消。排队超过 15 秒仍明确失败，不无限等待。

这些限制严于 Agent 的固定 60 秒 120 次预算。单会话 1000 次主进程预算、1024 次 Core 上限、字节计量、上传额度预留、最大在途数和未知写入不重放均保持。取消排队请求不计为原生派发；取消已派发请求仍保留实际在途占用，直到 native 结束。

短轮询不能保证模型立即完成。它让其他请求有机会使用串行通道；持续模型任务仍受模型推理速度、服务端四任务并发和会话配额约束。

## 验证与边界

新增串行 peer 回归，覆盖三项页面读取、挂起 poll 与快 JSON/心跳/取消共存；另覆盖滚动窗口边缘、失败重试计数、控制余量及取消后的实际在途释放。200 MiB 上传和 240 token SSE 的完整生产 JS 调用链继续回归。

定向结果：200 MiB/400 块在虚拟时钟约 258 秒完成，滚动窗口最高 93 次；这不是实际 P2P 上传吞吐。控制余量使持续大传输较旧合成约 243 秒略慢，换取普通页面短突发与心跳/取消可用性。

最终完整宿主测试 136 项通过，客户端集成与桌面构建 6/6 阶段通过。独立审核发现的满桶空闲相位问题已修复：第 599 ms 消耗满桶后，下个令牌在 1199 ms 补充；新增整数/小数非零相位回归，并给虚拟时钟测试增加独立步数上限。

北京时间 11:21 重启最终版后，重新登录并连接同一公司盒子。真实页面请求批次观察如下（均为成功请求；不含 DOM 绘制时间）：

| 请求批次 | 修复前 | 最终版 |
| --- | --- | --- |
| 4 项 start + 4 项 poll | 4.247 秒 | 1.674 秒；连续切页另有 3.336 秒样本 |
| 5 项 start + 5 项 poll | 5.474 秒 | 1.843 / 1.884 / 3.203 秒 |

这证明页面请求的固定排队等待明显缩短，不构成每个页面在任何负载下的耗时保证。连续切页、突发额度耗尽、后端处理和模型任务仍会影响耗时。界面同时存在人工操作，可访问性状态的观测有滞后，最终对比采用盒端从首个请求开始至末个响应结束的时间，不把不稳定的 UI 采样宣称为精确首屏延迟。

盒端 DE、worker 和 Agent 本轮均未改动；只重启桌面以加载两个宿主模块。部署回退和原始耗时记录位于 Data Engine `docs/development/OFFICE-BOX-INTEGRATION-0907.md` 与 `ZHIJUN-PERFORMANCE-0907.md`。临时请求计时仅含路由分类与耗时，不记录业务正文、账号凭据或证明头。
